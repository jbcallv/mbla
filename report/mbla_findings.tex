\section{The problem in one example}
An assistant agent can read and write every repository in a company's GitHub account. A user asks it to
summarize one public issue, and it hands that job to a second agent. If the second agent receives the
assistant's full access, a malicious message hidden in that issue can trick it into copying a private
repository into a public comment. Nothing was hacked; the agent simply held far more access than the task needed.

mbla decides, for each handoff, which permissions the receiving agent actually needs (here: read one
issue, and connect to GitHub) and grants only those.

\section{How it works}
\begin{enumerate}
  \item \textbf{Start from what the sender has.} mbla only ever picks from the permissions the handing-off
    agent already holds, so it can never give away more than that agent has.
  \item \textbf{Pick what the task needs.} A model reads the task and rates each available permission.
    Highly rated ones are granted. Ones rated as plausible go on a backup list.
  \item \textbf{Apply the receiver's own limits.} Whatever the receiving machine's operator refuses to allow is removed.
  \item \textbf{Handle mistakes.} If the agent is blocked partway through, it can ask for one specific missing
    permission. It gets it only if the sender holds it and it is on the backup list, with at most three requests per task.
\end{enumerate}
Steps 1 and 3 are fixed checks that do not depend on the model. If the model makes a bad choice, the task
may need an extra request or may fail, but the agent still cannot get more than the sender holds and the
receiver allows.

\section{Words used in this report}
\begin{description}
  \item[Permission] One specific allowed action, e.g.\ ``read issue 42 in acme/web'', ``connect to
    api.github.com'', ``write files in /artifacts'', or ``run make''.
  \item[Extra granted] Of the permissions the agent could have received but did not need, the share it
    received anyway. 0\% means it got only what it needed; 100\% means it got everything the sender had.
  \item[Needed but missed] Of the permissions the task needed, the share left out. The agent can still ask
    for these later, at the cost of a delay.
  \item[Exactly right] The share of tasks where the granted set matched the needed set exactly.
  \item[Attacks that get through] We planted attack goals in each task (for example ``read the private
    repository''). This is the share of those a compromised agent could still achieve by asking for missing
    permissions.
  \item[Time] How long the model takes to decide the permissions for one handoff, measured with each model
    running alone on one graphics card.
  \item[LLM] A large language model that reads the task and writes out the list of permissions it needs.
  \item[Yes/no scorer] A smaller, faster model that answers ``is this permission needed?'' for each permission separately.
  \item[Simple rule] No model: grant everything, grant what the receiver's operator says the operation
    usually needs (``operator list''), or grant things whose names appear in the task text.
\end{description}

\section{What should we use?}
\begin{itemize}
  \item \textbf{Best overall: Qwen3-8B (an LLM) with the backup-list rule.} Grants about 9\% extra, misses
    about 3\%, and lets only 13\% of attacks through (versus 100\% under the paper's current rule), while
    97\% of normal tasks still finish. Takes about 0.8 seconds per handoff.
  \item \textbf{If speed matters most: Qwen3-30B-A3B (an LLM).} Similarly tight (7\% extra) in about 0.3
    seconds, but the backup-list rule does not help it, because it rates permissions as simply yes or no.
  \item \textbf{If no model server is available: the operator list.} Almost never grants extra (2\%), but
    misses 19\% of needed permissions, so agents will ask for more often.
  \item \textbf{Avoid:} the tiny models (Qwen3-0.6B, Qwen3-1.7B, Phi-4-mini) and the off-the-shelf yes/no
    scorers Laya and CLM. They grant most of what the sender has.
  \item \textbf{Always keep the fixed checks on.} They are what keeps the system safe; the model only makes it tighter.
\end{itemize}

\section{Results}

\paragraph{Asking for more permissions is where attacks get through.}
Under the paper's current rule (grant any requested permission the sender holds), a compromised agent
could carry out every planted attack, with every model. Granting only what the model had already rated
plausible stops most of them.

\paragraph{The results hold up on outside data.}
FORTIS is a benchmark built by another research group for the same question: does an agent pick the least
powerful option that still does the job? On choosing one skill, the yes/no scorer Qwen3-Reranker-8B does as
well as LLMs ten times its size. Choosing a set of tools is hard for every model.

\paragraph{Showing the model the operator's list helps.}
Telling Qwen3-8B what the receiving operator says an operation usually needs cuts extra permissions from
about 23\% to 9\%. Moving the confidence cutoff trades extra permissions against missed ones; the LLMs reach
low values on both, the yes/no scorers do not.

\section{Why we trust these numbers}
\begin{itemize}
  \item \textbf{A human-checked answer key.} Two people independently marked which permissions each task
    needs, then settled their disagreements together (Table~\ref{tab:audit}).
  \item \textbf{No peeking.} Model settings were tuned on separate practice tasks; the test tasks were
    locked before any model saw them.
  \item \textbf{Outside data.} The FORTIS results come from another group's benchmark and grading code.
  \item \textbf{Checked checks.} The fixed safety checks agreed with an independently written version on
    14,480 generated cases, with zero mistakes.
\end{itemize}
